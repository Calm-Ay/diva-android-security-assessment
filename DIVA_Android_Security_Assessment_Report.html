03 / EVIDENCE

Storage and hardcoded secrets

01

Sensitive logging

The checkout flow logged a submitted payment-card value under the `diva-log` tag.

E diva-log: Error while processing transaction with credit card: [REDACTED TRAINING CARD]

Fix: Do not log sensitive values. Use structured redaction and disable verbose diagnostics in release builds.

02

Java hardcoding

`HardcodeActivity.access()` compared user input to a string embedded directly in the client. The recovered training key granted access.

Static review: input.equals("[REDACTED TRAINING KEY]")
Dynamic confirmation: DIVA displayed “Access granted!”

Fix: Keep long-lived secrets and authorization decisions off the client; validate on a server using short-lived, scoped credentials.

03–06

Plaintext storage

Credentials were recovered from four locations. App-private mode reduces routine cross-app access but does not protect plaintext after root compromise, backup exposure, or device extraction. External storage widened exposure.

SharedPreferences: /data/data/jakhar.aseem.diva/shared_prefs/...xml
SQLite: /data/data/jakhar.aseem.diva/databases/ids2
Private file: /data/data/jakhar.aseem.diva/uinfo*tmp
External storage: /sdcard/.uinfo.txt

SQLite validation: SELECT rowid, user, password FROM myuser;

Fix: Avoid persisting passwords. Minimize retention, use app-private storage, and protect necessary secrets with Android Keystore-backed cryptography. Never place secrets on shared storage.

04 / EVIDENCE

Input validation failures

07

SQL injection

The search workflow constructed a query from user input. A single crafted predicate returned all three seeded records, including password and payment fields.

Input: ' OR '1'='1' --
Observed result: all 3 seeded user records returned

Fix: Use parameterized queries or Android selection arguments. Minimize returned data and do not persist unnecessary sensitive fields.

08

Unsafe URI / WebView handling

The WebView rendered supplied HTML from a `data:` URI. No scheme or trusted-host allow-list protected the input.

Input URI: data:text/html,<h1>DIVA_URI_TEST</h1>
Observed result: WebView rendered DIVA_URI_TEST

Fix: Parse with `Uri`, allow only required HTTPS hosts, disable JavaScript unless needed, and avoid privileged bridges to untrusted content.

Why this matters

Input validation is a boundary control. SQL injection altered query logic, while unsafe URI acceptance gave untrusted content a rendering surface.

05 / EVIDENCE

Broken Android component access control

09

Exported credential activity

An unprivileged Android shell caller invoked the implicit activity action directly, bypassing normal application navigation and opening a credential screen.

Caller: Android shell UID (non-root)
Action: jakhar.aseem.diva.action.VIEW_CREDS
Observed result: API credential screen opened

Fix: Mark sensitive activities non-exported. If inter-app access is necessary, enforce signature permissions and authorize the caller in the receiving component.

10

Intent extra bypass

The credential activity trusted the attacker-controlled `check_pin` extra. Passing `false` skipped the normal PIN flow.

Action: jakhar.aseem.diva.action.VIEW_CREDS2
Extra: check_pin=false
Observed result: protected credential screen opened

Fix: Treat every Intent extra as untrusted. Determine authorization from trusted state and enforce it inside the target component.

11

Exported NotesProvider

The UI PIN protected only the in-app route. The exported ContentProvider allowed a shell caller to read every note directly.

content query --uri content://jakhar.aseem.diva.provider.notesprovider/notes
Observed result: 6 private notes returned

Fix: Keep providers non-exported by default. Apply signature-level permissions, validate callers, and restrict URI operations.

06 / RUNTIME ANALYSIS

Frida repair and native analysis

Initial condition

Frida 17.7.3 process enumeration worked, but every attach or spawn session closed. The target was a rooted Android 11 x86_64 Genymotion image and SELinux was permissive.

Root cause

Android Logcat recorded the Frida server aborting during injection with Unsupported Android linker. This was an emulator/runtime compatibility issue, not an application defense.

Resolution: a version-matched Frida 16.6.6 Python environment and Android x86_64 server were isolated from the broken Frida 17 setup. Attach, script load, and `Java.perform` then succeeded.

Native hardcoded secret

The Java activity passed user input to `DivaJni.access(String)`. Native string extraction identified the candidate value, the app accepted it, and Frida proved the plaintext argument reached the JNI method and returned success.

strings -a resources/lib/x86_64/libdivajni.so
…
Java_jakhar_aseem_diva_DivaJni_access
[REDACTED TRAINING VALUE]

Fix: Native code can raise reverse-engineering cost but cannot provide durable secret storage. Move sensitive validation to a trusted server.

07 / REMEDIATION

Priority remediation plan

PriorityActionAddresses
1Remove long-lived secrets, credential checks, and sensitive business decisions from the client.Hardcoding 1 and 2; PIN bypass
2Make sensitive Android components non-exported. Use signature permissions and caller validation only where sharing is required.Activities and NotesProvider
3Replace SQL concatenation with parameterized statements / selection arguments.SQL injection
4Eliminate password retention; encrypt necessary sensitive values with Android Keystore-backed keys.Storage 1–4
5Apply URI scheme and host allow-lists before opening WebView content.Unsafe URI handling
6Remove sensitive logging and implement release-safe logging standards.Insecure logging

Key lesson

Mobile apps operate in attacker-controlled environments. Client-side controls can support security, but they cannot be the final authority for secrets or authorization. Secure designs assume the package can be inspected and the process can be instrumented.
